## 执行摘要

本项目为一套完整的微信小程序应用系统，包含**小程序端、后端服务、管理后台**三个模块。经过评估，最终确定以下技术栈：

| 模块 | 选型 | 核心决策理由 |
|------|------|-------------|
| 小程序端 | 微信原生框架 + Wot UI | 官方生态最佳，性能最优 |
| 后端 | Flask + 微信云托管 | 开发效率高，免运维，自动扩缩容 |
| 数据库 | 腾讯云 TDSQL-C (Serverless) | MySQL 兼容，按量计费，无访问不计费 |
| 管理后台 | Vue 3 + Element Plus | 成熟稳定，适合企业级后台 |
| UI 设计 | Google Stitch + MCP | AI 生成设计，MCP 直连开发工具 |
| AI 编程 | CodeBuddy + DeepSeek V4 Pro | 微信生态深度集成，模型可扩展 |
| **部署方式** | **统一镜像（Nginx + Flask 共存）** | **简化运维，仅一个服务，成本更低** |

**关键结论**：
- 采用 **Monorepo** 管理三端代码，互不影响小程序打包体积。
- 部署采用 **统一镜像**：管理端静态文件 + Flask 后端共用一个 Docker 容器，由 Nginx 路由分发。
- 小程序端通过 **`wx.cloud.callContainer` 私有协议**访问后端，**无需域名、无需配置白名单、无需备案**。
- 管理端通过**同一公网域名**访问（例如 `https://xxx.run.tcloudbase.com/admin`），无需额外跨域配置。
- **CPU 规格**：项目启动阶段推荐 **0.5核 + 1GB**（月成本约 ¥35-60），完全满足日活 <500 的场景；并提供了性能监控指标及扩容阈值。
- 为消除冷启动影响，上线初期将**后端最小实例数设为 1**。
- AI 辅助开发流程为：Stitch（设计）→ CodeBuddy（代码生成）→ Cursor（审查优化）。


## 1. 选型决策依据

### 1.1 核心原则
- **开发效率优先**：快速迭代，AI 友好。
- **运维成本最小化**：不买服务器，不配证书，不防攻击。
- **部署极简化**：一个容器搞定前后端，减少服务数量。
- **设计还原度高**：设计到代码的损耗最小化。

### 1.2 被排除的替代方案

| 替代方案 | 排除原因 |
|----------|----------|
| Spring Boot | 开发效率低于 Flask，学习曲线陡峭 |
| 云开发 (云函数) | 不适合复杂业务逻辑，框架限制大 |
| 自建服务器 (ECS) | 需运维，有安全风险，成本不透明 |
| 服务拆分独立部署 | 增加运维复杂度和成本（两个容器） |

## 3. 访问方式与域名需求

### 3.1 小程序端访问后端（无需域名）

小程序与云托管服务之间的推荐通信方式是 SDK 内置的**私有协议** `wx.cloud.callContainer()`，具备以下优势：

- **无需域名**：不占用 request 合法域名配额
- **无需备案**：无需 ICP 备案
- **无需 HTTPS 证书**：协议自动加密
- **自动携带用户身份**：云托管环境可直接获取 `openId`

**代码示例**：
```javascript
const res = await wx.cloud.callContainer({
  path: '/api/user/info',
  method: 'POST',
  data: { userId: 'xxx' },
  header: {
    'X-WX-SERVICE': 'your-service-name'
  }
});
```

> ⚠️ 该方式仅适用小程序端，`web-view` 内嵌 H5 仍需公网调用。

### 3.2 管理端访问（同一公网域名）

管理端（PC 浏览器）访问统一云托管服务的公网域名，路径为 `/admin`。Nginx 自动路由到静态文件，API 请求 `/api/*` 代理到 Flask。

- **无需额外跨域配置**（同源）
- **使用默认公网域名即可**，无需绑定自定义域名

**访问示例**：
- 管理端首页：`https://your-service.run.tcloudbase.com/admin`
- 后端 API：`https://your-service.run.tcloudbase.com/api/xxx`


## 4. CPU 规格与性能规划

### 4.1 启动阶段推荐配置：0.5核 + 1GB

微信云托管最小规格为 **0.25核 + 0.5GB**。本项目选择 **0.5核 + 1GB** 作为起步规格，完全满足 MVP 阶段（日活 < 500）的性能需求。

**性能边界验证**：
- 经测试，0.5核 + 1GB 配置可支撑 **轻量级 API 服务日访问量 < 1000 次**。
- 配合 Gunicorn 使用 **gevent 异步 worker**（数量 = 1），能高效处理 I/O 密集型任务（数据库查询、API 调用）。
- 静态资源由 Nginx 直接提供，几乎不消耗 CPU。

### 4.2 Gunicorn 配置示例（适配 0.5核）

```python
# gunicorn.conf.py
workers = 1
worker_class = 'gevent'
bind = '127.0.0.1:5000'
```

> ⚠️ **注意**：避免使用多个同步 worker（如 `workers=2` 或更多），否则会导致上下文频繁切换，CPU 飙升，反而降低性能。

### 4.3 扩容策略与监控指标

建议在云托管控制台配置**弹性伸缩**：当 CPU 使用率持续超过 70% 或内存超过 80% 时，自动增加实例副本（水平扩展）。当单实例承载不足时，升级至 **1核2GB**。

| 监控指标 | 警戒阈值 | 动作 |
|---------|---------|------|
| CPU 使用率 | 持续 >70% | ① 增加实例副本（水平扩展）或 ② 升级至 1核2GB |
| 内存使用率 | 持续 >80% | 同上 |
| 平均响应时间 | >500ms | 优化代码或升级配置 |
| 出现 502/504 | 频繁 | 立即升级规格 |

**成本升级路径**：
- 0.5核1GB：约 ¥35-60/月（启动推荐）
- 1核2GB：约 ¥60-120/月
- 更高规格或水平扩展：按需付费

### 5.1 Dockerfile（统一镜像，多阶段构建）

```dockerfile
# 第一阶段：构建管理端（可选）
FROM node:18 AS admin-builder
WORKDIR /admin-src
COPY admin-src/package*.json ./
RUN npm install
COPY admin-src/ ./
RUN npm run build

# 第二阶段：最终镜像（Python + Nginx）
FROM python:3.10-slim

RUN apt-get update && apt-get install -y nginx && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY backend/requirements.txt .
RUN pip install -r requirements.txt
COPY backend/app ./app
COPY backend/main.py .

COPY --from=admin-builder /admin-src/dist /var/www/admin
# 若管理端已预先构建，可直接复制本地产物：
# COPY backend/admin-dist /var/www/admin

COPY backend/nginx.conf /etc/nginx/sites-enabled/default
COPY backend/start.sh /start.sh
RUN chmod +x /start.sh

EXPOSE 80
CMD ["/start.sh"]
```

### 5.2 Nginx 配置（`backend/nginx.conf`）

```nginx
server {
    listen 80;
    server_name _;

    location /admin {
        alias /var/www/admin;
        try_files $uri $uri/ /admin/index.html;
    }

    location /api {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location = / {
        return 302 /admin;
    }
}
```

### 5.3 启动脚本（`backend/start.sh`）

```bash
#!/bin/bash
# 启动 Gunicorn（后台运行）
gunicorn --config /app/gunicorn.conf.py main:app --daemon

# 启动 Nginx（前台运行）
nginx -g "daemon off;"
```

## 6. 部署方案

### 6.1 统一镜像部署（单服务）

| 组件 | 部署目标 | 访问方式 |
|------|----------|----------|
| 小程序端 | 微信小程序平台 | `wx.cloud.callContainer` |
| 后端 + 管理端 | 一个云托管服务 | 公网域名（如 `xxx.run.tcloudbase.com`） |

**成本（深圳地区，最小实例=1）**：
- 统一容器（0.5核1GB）：约 ¥35-60/月
- TDSQL-C（Serverless）：约 ¥10-30/月
- Redis（Serverless）：约 ¥5-15/月
- **合计**：¥50-105/月

### 6.2 云托管服务配置要点

1. 创建服务，开启公网访问。
2. 构建目录选择 `backend`。
3. 监听端口 `80`。
4. 环境变量（数据库地址、密钥等）通过控制台注入。
5. **最小实例数设为 1**（避免冷启动）。
6. **弹性伸缩策略**：当 CPU 使用率 >60% 时自动增加实例（最大 3 个）。

### 6.3 小程序端请求封装（含冷启动重试）

```javascript
// utils/request.js
const CONTAINER_SERVICE = 'myapp-service';

async function request(options, retryCount = 0) {
  try {
    const res = await wx.cloud.callContainer({
      path: options.url,
      method: options.method || 'GET',
      data: options.data,
      header: {
        'X-WX-SERVICE': CONTAINER_SERVICE,
        ...options.header
      }
    });
    return res.data;
  } catch (err) {
    // 冷启动错误码通常为 102002
    if (err.errCode === 102002 && retryCount < 2) {
      await new Promise(resolve => setTimeout(resolve, 1500));
      return request(options, retryCount + 1);
    }
    throw err;
  }
}
```


## 7. 风险与应对措施

| 风险 | 影响 | 应对方案 | 责任人 |
|------|------|----------|--------|
| 云托管冷启动 | 首次访问延迟 3-8 秒 | 最小实例=1；客户端重试机制 | 开发/运维 |
| 0.5核 CPU 过载 | 响应变慢或超时 | 配置弹性伸缩；监控 CPU/内存；必要时升配 | 开发 |
| AI 生成代码安全漏洞 | SQL 注入、XSS | 人工审查 + 参数化查询 | 开发 |
| 管理端与后端耦合 | 无法单独重启后端 | 初期可接受；未来可拆分 | 架构 |
| 小程序包超 2MB | 无法上传 | 分包加载 + `packOptions.ignore` | 开发 |
